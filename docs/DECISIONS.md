### Visual/token decisions (export wins, `docs/DESIGN.md` updated)

1. **Border opacity** — DESIGN.md said a single `--color-border: .09` / `--color-border-strong: .18`. Export uses `.08` as the default on cards/hero frames/features, `.09` on nav/pills/contact rows, and three different hover targets depending on component (`.22` cards/rows, `.34` outline buttons). Updated the token to `.08` default and noted the variants in prose rather than adding more tokens (KISS/YAGNI).
2. **New token: `--color-media-fill: #1b1b1f`** — the screenshot/media-placeholder frame fill used throughout the export; DESIGN.md had no token for it.
3. **Focus ring offset** — DESIGN.md said 2px ring / 2px offset. Export's CSS (`:focus-visible{outline:2px solid #ef233c;outline-offset:3px}`) uses a 3px offset. Updated to match the export.
4. **"Tile" radius (20px)** — present in the export's own token reference sheet, but no live component in `Portfolio.dc.html` or `Project Page.dc.html` actually uses it; every real card/article/modal is 24px. Decision: do not add a third radius token — documented as unused/reserved (YAGNI). If a future component genuinely needs a 20px tile, add it then.
5. **Reveal motion timing** — DESIGN.md gave a range (`translateY` 8–12px, 0.4–0.6s ease-out). Export's own motion spec (Overview.dc.html, "Components and motion" section) states one exact value: `translateY 10px → 0, .7s ease`. Updated DESIGN.md to the exact value.
6. **Bottom vignette implementation** — DESIGN.md described it as `position: fixed` on the viewport. The export implements it as `position: sticky; bottom: 0; margin-top: -140px` nested inside each page's root div. Same visual result (a 140px fade pinned to the bottom of the viewport while content is shorter than the viewport, and to the bottom of the page once it's taller), different CSS technique. Decision: document the export's technique as the one to build, since it's simpler to reason about inside a single-page layout than a true viewport-fixed element that must track `z-index` against the nav/modal.
7. **Typography is two directions, not one** — DESIGN.md's text implied a single pairing was "chosen in the design export." The export actually shows two parallel, fully-specified directions (1a: Geist/Geist Mono, 8pt rhythm, plain titles; 1b: Instrument Sans/JetBrains Mono, 12pt rhythm, numbered eyebrows), with neither marked as the pick. **Resolved 2026-10-11: Rachmad confirmed direction 1a.** DESIGN.md section 2 updated to state 1a as final rather than a fallback-pending-confirmation; the 1b column is kept in the comparison table for reference only.

## 2026-10-11 — Phase 1 foundation

1. **`src/proxy.ts` used instead of `src/middleware.ts`.** `pnpm build` on Next.js 16.4.0 emits: "The 'middleware' file convention is deprecated. Please use 'proxy' instead." Confirmed via Next's own build-time static-info parser (`get-page-static-info.js`) that a root `proxy.ts` with the same default-export function shape (here, `next-intl`'s `createMiddleware(routing)`) is the convention this Next version expects — exactly the ambiguity `docs/ARCHITECTURE.md` section 4 flagged in advance ("use whichever the installed version expects").
2. **`Content-Security-Policy` loosened to allow `'unsafe-inline'` for `script-src` and `style-src`, plus `data:` for `img-src`/`font-src`.** The strict `default-src 'self'` CSP written in Phase 0 (before there was any real page to test against) blocked Next.js's own inline hydration bootstrap scripts outright — confirmed via the browser console (`Executing inline script violates ... Content-Security-Policy`) and by observing that React never hydrated as a result (scroll-spy, the mobile menu, and the language toggle's client behavior were all inert until this was fixed). No nonce-based CSP infrastructure exists in this project, and `docs/ARCHITECTURE.md` says to "keep the CSP simple, since there are no third-party embeds" — `'unsafe-inline'` is the standard, accepted trade-off for a static Next.js site without nonce plumbing. `data:` was added for `next/font`'s self-hosted font delivery and ASSETS.md's code-generated SVG placeholders.
3. **Left `'unsafe-eval'` out of the CSP**, even though the dev server's console shows a `Console Error` overlay for it ("eval() is not supported in this environment... React requires eval() in development mode ... React will never use eval() in production mode"). Verified via the Next.js dev tools issue overlay that this is the only remaining issue and is explicitly dev-only tooling (Fast Refresh stack-trace reconstruction), not something that reaches production — adding `'unsafe-eval'` would be a real CSP regression for a cosmetic dev-console message.
4. **Scroll-spy implemented with a single `IntersectionObserver` and `rootMargin: "-45% 0px -45% 0px"`** (a thin horizontal band through the viewport's vertical center) rather than a scroll-position calculation, keeping `Nav.tsx` free of manual scroll-offset math. Verified working end-to-end in a real browser (Chrome DevTools MCP): programmatically scrolling to `#skills` correctly applies the accent underline to the "Skills" nav link and no other.
5. **Desktop/mobile nav variants both render unconditionally, toggled via Tailwind's `hidden md:flex` / `md:hidden`**, instead of a JS-computed `ResizeObserver`-driven boolean like the export's canvas runtime uses. Avoids a redundant resize listener; Tailwind's CSS-only breakpoint switching is simpler and still correct for SSR (no layout flash, no JS-dependency for the correct variant to show).

3. **Found and fixed a real bug during browser testing: the carousel's pause-on-hover/focus never fired.** `ProjectCard`'s "whole card is one link" requirement is implemented via a stretched-link `::after` pseudo-element (the `<a>` wraps only the title text, with `after:absolute after:inset-0` extending its clickable/hoverable area over the whole card) — standard practice for single-link cards. But this means the `<a>`'s stretched area physically sits on top of the media region in hit-testing, so a `ProjectCarousel` component tracking its own `onMouseEnter`/`onMouseLeave` never received those events; confirmed via `document.elementFromPoint` returning the `<a>`, not the carousel's wrapper div, at the media area's center. Verified the fix with real CDP-level mouse hover/leave and keyboard focus, each checked against which carousel slide was actually visible (`opacity:1`), after an initial flawed test (checking the first-matching DOM node's text, which never changes) gave a false negative.
4. **`ProjectMedia.tsx` repurposed from a server component into a plain data-resolving function** (`resolveProjectMedia`), with a new `ProjectMediaView.tsx` doing the actual client-side rendering. Required by the fix in #3: a Server Component can pass pre-rendered JSX or plain serializable data to a Client Component as props, but not functions/closures, and the existsSync check must run server-side while the hover-driven `paused` prop must reach the carousel from a client ancestor — splitting resolution (server) from rendering (client) is the only way to satisfy both.

## 2026-10-11 — Phase 5 Project pages and modal

1. **`ProjectContent` is variant-aware (`"page" | "modal"`), not byte-identical between the two wrappers.** `docs/ARCHITECTURE.md` section 4 says "the modal and the full page render the same `ProjectContent` component. 2. **Found and fixed a cross-cutting bug while building the first non-home routes: `Nav`'s section links used bare `#id` hrefs**, which only ever worked by accident because every previous phase's testing happened on the home page. Visiting a project page would have made every nav link a dead in-page anchor jump to nothing. 3. **Native `<dialog>` + `showModal()` delivers focus-trapping, Esc-to-close, inert background, body-scroll-lock, and focus-restore-on-close entirely for free**, per the HTML living standard — confirmed by testing each one directly (focus landed on the Close button on open; scroll position matched exactly before/after open+close via all four close paths; `document.activeElement` was the originally-clicked card's link immediately after closing). 4. **The modal's Close button is a native `<form method="dialog"><button>` rather than a client `onClick` handler** — closing a `<dialog>` via form submission is standard HTML, needs no JS, and funnels through the same `close` event listener as Esc/backdrop/`.close()`, so there's exactly one code path for "the modal closed" regardless of which UI triggered it.

A soft transition to the same href that's already intercepted would just re-render the same modal; a hard navigation is required to actually land on the real, non-intercepted full page — matching the control's explicit intent ("Open project page").
6. **Prev/next cycling order (both the full page and the modal) walks the single `projects` array** (featured tier first in card order, then other tier, each internally ordered), not separate per-tier cycles — so "Next" from the last featured project goes to the first "other" project, and wrapping from the very last project returns to the very first. Not specified by any doc; a reasonable default given there's only one documented ordering (the gallery's own tier+order sort) to walk.

## 2026-10-11 — Phase 5 follow-up: concept cards as live components

`docs/ASSETS.md` and `docs/ARCHITECTURE.md` assumed the three concept cards (Quickbill Embedded Payment, AccelByte Multiplayer Servers, Maybank Digital Branch) would ship as exported videos. The design export instead has them as three live HTML/JS animations (`design/export/Concept{EmbeddedPayment,MicroFrontend,Multiplayer}.dc.html`), ported as React/SVG/Motion components (`src/components/projects/concepts/`).

1. **SVG scaling uses `viewBox` + CSS `width/height: 100%`, not the export's manual `ResizeObserver` + JS scale-factor technique.** Simpler, dependency-free, and visually identical — an improvement over the source, not a deviation in output.
2. **Color "heat" animation uses numeric `fillOpacity`/`strokeOpacity` tweens on a fixed `var(--color-fg)`, not the export's `color-mix()`-style string interpolation.** Motion can't smoothly tween arbitrary CSS function strings; opacity tweening on one token produces the same visual ramp while only ever touching a design token, never a hardcoded color.
3. **Multiplayer's log panel scrolls continuously through a doubled 6-message array, instead of the export's per-line identity-swap-with-opacity-blend.** Disclosed simplification — same "live log" impression, fewer moving parts.
4. **Playback restarts from the beginning each time the component re-enters the viewport**, rather than true pause/resume from the exact frame. `useInView` + `useReducedMotion` gate a `playing` boolean that Motion's keyframe arrays restart on; matches the Reveal-once pattern already used elsewhere on the site and respects `prefers-reduced-motion`.
5. **Fidelity verdict: all three ported without needing the optional `webm`/`mp4`/`poster` fallback** added to the `concept` media type for this reason — `resolveProjectMedia` still checks for those files first (existsSync-gated) in case a future concept can't be ported live, but none of the three needed it.
6. **`docs/ASSETS.md`'s three `public/media/concepts/*.{webm,mp4,jpg}` placeholder rows were removed** — they described assets that no longer apply, now that these three render as live components with no video fallback in use.

## 2026-10-12 — Fixed a real border-color regression from the theme work, plus nav/toggle animation

Rachmad reported the border color had visibly changed in the navbar, buttons and cards, and that light-mode borders looked too strong. Both were caused by one real bug in the previous commit's `rgba(var(--overlay-rgb),N)` conversion — **two separate mistakes stacked**, not one:

1. `rgba(var(--overlay-rgb),0.09)` mixes the modern space-separated color-channel syntax (`--overlay-rgb: 255 255 255`) with the legacy comma-before-alpha syntax — invalid CSS. The browser dropped the whole `border-color` declaration, so it fell back to its initial value, `currentColor` (the element's text color) — explaining both symptoms exactly: in dark mode this swapped the intended ~9% white border for a full-opacity near-white text-color border (visibly different); in light mode it swapped it for a full-opacity near-black text-color border (reads as "too strong").
2. Fixing the comma-vs-slash syntax alone (switching to `rgb(var(--overlay-rgb) / 0.09)`) still didn't work, for an unrelated reason: Tailwind's arbitrary-value bracket syntax (`[...]`) cannot contain literal spaces — a raw space inside `[...]` terminates the class token when Tailwind scans the className string, so the utility was never generated at all (confirmed via the compiled CSS: zero `rgb(var(...))` rules existed anywhere in the stylesheet). The fix requires Tailwind's underscore-for-space convention: `rgb(var(--overlay-rgb)_/_0.09)` — Tailwind converts `_` back to a literal space when it emits the final CSS rule, so the generated stylesheet is correct, modern CSS (confirmed: compiled output contains `rgb(var(--overlay-rgb) / .09)` with real spaces).

Both fixes applied across all 11 files that reference `--overlay-rgb`; `TimelineNode.tsx`'s one usage is a genuine inline JS style string (not a Tailwind class), so it keeps literal spaces correctly and needed no change. Verified via `getComputedStyle` in a live browser, in both themes: dark mode's nav/card/button borders now resolve to the exact original pre-theme values (e.g. `rgba(255, 255, 255, 0.09)`, `rgba(255, 255, 255, 0.16)`); light mode resolves to the equivalent black-based opacity (e.g. `rgba(10, 10, 12, 0.09)`) instead of a full-opacity fallback.

## 2026-10-12 — Fixed the language-pill flicker introduced by the previous `layoutId` approach

Rachmad reported the active-language background flickering across the whole screen when clicking any nav menu item. Root cause: `LanguageToggle`'s sliding pill used Framer Motion's `layoutId` shared-element animation, which measures element position via `getBoundingClientRect()` — viewport-relative. This has no dependency on document/viewport position at all, so the whole bug class is structurally impossible now, not just harder to trigger. ## 2026-10-13 — Removed localization entirely: English-only, no next-intl

Rachmad asked to remove the localization feature, `next-intl`, and the language switcher outright, shipping English-only. This directly reverses `CLAUDE.md`'s original "Both locales ship together" non-negotiable rule and the bilingual (EN/ID) architecture documented across `docs/ARCHITECTURE.md` — a deliberate full reversal, not an oversight, given the instruction was explicit and unambiguous. `CLAUDE.md` and `docs/ARCHITECTURE.md` were updated in the same pass to describe the new English-only architecture as current, not as a historical note.

1. **Removed the `next-intl` package** (`pnpm remove next-intl`) and its config wiring in `next.config.ts` (the `createNextIntlPlugin` wrapper).
2. **Deleted the entire i18n layer**: `src/i18n/{routing,navigation,request}.ts`, `src/messages/{en,id}.json`, `src/proxy.ts` (the next-intl locale-detection middleware), and `src/components/layout/LanguageToggle.tsx`.
3. **Flattened `src/app/[locale]/` up to `src/app/`** — `layout.tsx`, `page.tsx`, `not-found.tsx`, `opengraph-image.tsx` and `projects/[slug]/page.tsx` all lost their `locale` param/`setRequestLocale` calls and now live at the plain route (`/`, `/projects/[slug]`, etc., no `/en` or `/id` prefix). `sitemap.ts` dropped its per-locale loop — one entry per page instead of one per locale per page.
4. **Flattened the entire content schema**: `Locale`/`Localized<T>` types removed from `src/content/schema.ts`; every `Project`/`Media`/`Company`/`SkillGroup` field that was `{ en: string; id: string }` (or `Localized<string[]>`) is now a plain `string`/`string[]`.
