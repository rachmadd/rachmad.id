# Decisions

Record of places where the design export (`design/export/`) disagreed with a documented value, or where the docs didn't cover something and a call had to be made. Per `CLAUDE.md`'s source-of-truth order, the export wins on visual/layout decisions; decisions below follow that unless noted otherwise.

## 2026-10-11 — Design import from Claude Design project "Portfolio overview and systems"

Imported via `/design-login` from `https://claude.ai/design/p/743b8ca5-e349-47bf-8844-632b0c55377f`. ### Visual/token decisions (export wins, `docs/DESIGN.md` updated)

1. **Border opacity** — DESIGN.md said a single `--color-border: .09` / `--color-border-strong: .18`. Export uses `.08` as the default on cards/hero frames/features, `.09` on nav/pills/contact rows, and three different hover targets depending on component (`.22` cards/rows, `.34` outline buttons). Updated the token to `.08` default and noted the variants in prose rather than adding more tokens (KISS/YAGNI).
2. **New token: `--color-media-fill: #1b1b1f`** — the screenshot/media-placeholder frame fill used throughout the export; DESIGN.md had no token for it.
3. **Focus ring offset** — DESIGN.md said 2px ring / 2px offset. Export's CSS (`:focus-visible{outline:2px solid #ef233c;outline-offset:3px}`) uses a 3px offset. Updated to match the export.
4. **"Tile" radius (20px)** — present in the export's own token reference sheet, but no live component in `Portfolio.dc.html` or `Project Page.dc.html` actually uses it; every real card/article/modal is 24px. Decision: do not add a third radius token — documented as unused/reserved (YAGNI). If a future component genuinely needs a 20px tile, add it then.
5. **Reveal motion timing** — DESIGN.md gave a range (`translateY` 8–12px, 0.4–0.6s ease-out). Export's own motion spec (Overview.dc.html, "Components and motion" section) states one exact value: `translateY 10px → 0, .7s ease`. Updated DESIGN.md to the exact value.
6. **Bottom vignette implementation** — DESIGN.md described it as `position: fixed` on the viewport. The export implements it as `position: sticky; bottom: 0; margin-top: -140px` nested inside each page's root div. Same visual result (a 140px fade pinned to the bottom of the viewport while content is shorter than the viewport, and to the bottom of the page once it's taller), different CSS technique. Decision: document the export's technique as the one to build, since it's simpler to reason about inside a single-page layout than a true viewport-fixed element that must track `z-index` against the nav/modal.
7. **Typography is two directions, not one** — DESIGN.md's text implied a single pairing was "chosen in the design export." The export actually shows two parallel, fully-specified directions (1a: Geist/Geist Mono, 8pt rhythm, plain titles; 1b: Instrument Sans/JetBrains Mono, 12pt rhythm, numbered eyebrows), with neither marked as the pick. **Resolved 2026-10-11: Rachmad confirmed direction 1a.** DESIGN.md section 2 updated to state 1a as final rather than a fallback-pending-confirmation; the 1b column is kept in the comparison table for reference only.

## 2026-10-11 — Phase 0 scaffolding

1. **`.github/workflows/ci.yml` created from scratch.** `README.md` and `docs/ARCHITECTURE.md` both assume this file already exists ("keep the existing `.github/`"), but no `.github/` directory was present in the repo. Wrote it per `docs/DEPLOYMENT.md` section 1 (lint, typecheck, build, Lighthouse CI against `lighthouserc.json`, triggered on PRs and pushes to `main`).
2. **Package manager and tool versions pinned to the newest mutually compatible set, not blindly "latest."** `pnpm@12.11.2` via Corepack. `next@16.4.0`, `react@19.3.0`, `react-dom@19.3.0`, `next-intl@4.14.9`, `motion@14.0.0` (not the just-published `14.1.0` — the npm registry's supply-chain `minimumReleaseAge` policy in this environment rejects packages published inside its lookback window; `14.1.0` was 2 days old and still inside it, so pinned to the next version back). `eslint@9.39.5` and `typescript@5.9.3` (not eslint 10 / typescript 7, which are the newest majors on the registry but unsupported by `eslint-config-next@16.4.0`'s bundled plugins — `eslint-plugin-react`, `eslint-plugin-jsx-a11y`, `@typescript-eslint/*` cap at eslint `^9` and typescript `<6.1.0`; confirmed via `pnpm peers check`).
3. **`eslint.config.mjs` uses `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript` imported directly as flat-config arrays, not the `FlatCompat.extends("next/core-web-vitals", "next/typescript")` pattern from older create-next-app scaffolds.** `eslint-config-next@16.4.0`'s `dist/*.js` already export native flat-config arrays (confirmed by requiring them directly and checking `Array.isArray`). Running them through `FlatCompat` double-wraps an already-flat config and crashes (`TypeError: Converting circular structure to JSON`) on `eslint-plugin-react`'s self-referencing flat config object.
4. **`design/**` excluded from ESLint scope.** The export's `support.js` (the Claude Design canvas runtime) trips several rules (`react/no-deprecated`, `@next/next/no-assign-module-variable`, unused vars). It's vendor reference material we don't edit or ship (`design/README.md`: "Never copy the exported HTML or CSS wholesale into `src/`"), so it's out of lint scope rather than "fixed."
5. **`agentRules: false` set in `next.config.ts`.** Next.js 16 auto-generates an `AGENTS.md` on `next dev`/`next build`. This project already has `CLAUDE.md` as its agent entry point and a full `docs/` tree; the auto-generated file is redundant, so generation is disabled and the one generated during Phase 0 verification was deleted.
6. **`pnpm-workspace.yaml` added with `allowBuilds`** for `@parcel/watcher`, `@swc/core`, `unrs-resolver` — native build scripts required by the Next.js toolchain that pnpm 12 blocks by default pending explicit approval.
7. **Node pinned to `24.18.0`** (`.nvmrc` plus `engines.node` in `package.json`) — the version actually installed in the dev environment; docs only said "Node LTS" without a specific version.

## 2026-10-11 — Phase 1 foundation

1. **`src/proxy.ts` used instead of `src/middleware.ts`.** `pnpm build` on Next.js 16.4.0 emits: "The 'middleware' file convention is deprecated. Please use 'proxy' instead." Confirmed via Next's own build-time static-info parser (`get-page-static-info.js`) that a root `proxy.ts` with the same default-export function shape (here, `next-intl`'s `createMiddleware(routing)`) is the convention this Next version expects — exactly the ambiguity `docs/ARCHITECTURE.md` section 4 flagged in advance ("use whichever the installed version expects").
2. **`Content-Security-Policy` loosened to allow `'unsafe-inline'` for `script-src` and `style-src`, plus `data:` for `img-src`/`font-src`.** The strict `default-src 'self'` CSP written in Phase 0 (before there was any real page to test against) blocked Next.js's own inline hydration bootstrap scripts outright — confirmed via the browser console (`Executing inline script violates ... Content-Security-Policy`) and by observing that React never hydrated as a result (scroll-spy, the mobile menu, and the language toggle's client behavior were all inert until this was fixed). No nonce-based CSP infrastructure exists in this project, and `docs/ARCHITECTURE.md` says to "keep the CSP simple, since there are no third-party embeds" — `'unsafe-inline'` is the standard, accepted trade-off for a static Next.js site without nonce plumbing. `data:` was added for `next/font`'s self-hosted font delivery and ASSETS.md's code-generated SVG placeholders.
3. **Left `'unsafe-eval'` out of the CSP**, even though the dev server's console shows a `Console Error` overlay for it ("eval() is not supported in this environment... React requires eval() in development mode ... React will never use eval() in production mode"). Verified via the Next.js dev tools issue overlay that this is the only remaining issue and is explicitly dev-only tooling (Fast Refresh stack-trace reconstruction), not something that reaches production — adding `'unsafe-eval'` would be a real CSP regression for a cosmetic dev-console message.
4. **Scroll-spy implemented with a single `IntersectionObserver` and `rootMargin: "-45% 0px -45% 0px"`** (a thin horizontal band through the viewport's vertical center) rather than a scroll-position calculation, keeping `Nav.tsx` free of manual scroll-offset math. Verified working end-to-end in a real browser (Chrome DevTools MCP): programmatically scrolling to `#skills` correctly applies the accent underline to the "Skills" nav link and no other.
5. **Desktop/mobile nav variants both render unconditionally, toggled via Tailwind's `hidden md:flex` / `md:hidden`**, instead of a JS-computed `ResizeObserver`-driven boolean like the export's canvas runtime uses. Avoids a redundant resize listener; Tailwind's CSS-only breakpoint switching is simpler and still correct for SSR (no layout flash, no JS-dependency for the correct variant to show).

## 2026-10-11 — Phase 3 Experience timeline

1. **Node positions computed directly from the same L/R/top/P formula used to build the SVG path (ported from the export's `geom(w, m)`), not sampled from the rendered path via `getPointAtLength`.** `docs/ARCHITECTURE.md` section 7 describes a `getPointAtLength`-after-layout approach; the export's own implementation (`design/export/Portfolio.dc.html`) places nodes at the exact vertices the Bézier path is built to pass through, which is simpler (no DOM measurement, no post-layout effect race), gives an identical visual result, and — critically — is a pure function that can be unit-tested directly, which the `getPointAtLength` approach cannot (it requires a live SVG in a real DOM). Same category of export-wins-on-implementation-technique precedent as the vignette (#6).
2. **`pnpm test` added (Node's built-in `node:test`/`node:assert`, zero new dependencies)**, wired into `.github/workflows/ci.yml` after `pnpm typecheck`. `docs/ARCHITECTURE.md`'s stack table names no test framework, and `CLAUDE.md` says to ask before adding a dependency not named there — but `docs/ROADMAP.md` Phase 3 explicitly requires `timeline-geometry.ts` to be "unit-tested for node ordering and no overlap with text areas." Verified Node 24's native TypeScript stripping runs `.ts` test files directly with no transpilation step; `tsconfig.json` gained `allowImportingTsExtensions: true` so `tsc --noEmit` accepts the test file's required explicit `.ts` import specifier (Node's ESM resolver, unlike the bundler, needs the extension).
3. **`src/lib/format-date.ts` added** (not in `docs/ARCHITECTURE.md`'s named `lib/` list) — a small `Intl.DateTimeFormat`-based helper implementing `docs/CONTENT.md` section 3's exact stated date-range format. Verified Node's Indonesian locale data produces the exact month abbreviations CONTENT.md lists (Jan, Feb, Mar, Apr, Mei, Jun, Jul, Agu, Sep, Okt, Nov, Des).
4. **`companies.ts` added a `projectCountStub` field instead of a computed project count.** `docs/ROADMAP.md` Phase 3 explicitly sequences Experience before Projects (Phase 4) and says to "stub the hook" for the "N projects →" link — no `src/content/projects/*.ts` exists yet to count from. Values are taken from `docs/CONTENT.md` section 3's table as-is, including vOffice's count, which that table itself marks "(to confirm)". Replacing this with a real computed count is flagged as Phase 4 work.
5. **Company logos render as a plain initials chip (`<span>QB</span>` styled as a dark rounded square), matching the export exactly, with no `next/image` or SVG file.** Same reasoning as the Phase 2 avatar decision (#4) — `public/logos/` doesn't exist in the repo, and `docs/CONTENT.md`'s `Company.logo` schema field is kept on the type for a future real-asset swap but is currently unused by any component.
6. **Found and fixed a no-JS regression affecting every `Reveal`-wrapped element since Phase 1, not just this phase's timeline.** Verifying Phase 3's explicit "no-JS fallback" requirement via raw SSR output (`curl`) surfaced that Framer Motion's `whileInView` animation renders its `initial` state (`opacity:0`) in the server-rendered HTML — correct for JS-enabled hydration, but it means any visitor whose JS never runs (or fails) sees the Intro heading, every section title, every Skills row, and the Contact body permanently invisible, since nothing ever triggers the opacity transition to 1. Fixed by tagging `Reveal`'s root element `data-reveal` and adding a `<noscript><style>[data-reveal]{opacity:1 !important;transform:none !important}</style></noscript>` block in `src/app/[locale]/layout.tsx`'s `<head>` — standard, dependency-free `<noscript>` CSS override, inert when JS runs normally. Confirmed via `curl` that the override renders in SSR output and that JS-enabled reveal animation still works correctly afterward.
7. **`.timeline-highlight` CSS class referenced by the "brighten project cards" click stub is not yet defined** — there is nothing in the DOM for it to target until Phase 4 adds `data-company-highlight="<slug>"` attributes to project cards, so defining its visual treatment now would be guessing at markup that doesn't exist yet. The click handler itself is fully wired and harmlessly no-ops today; the CSS rule is Phase 4 work.

## 2026-10-11 — Phase 4 Projects gallery

1. **Media files (image/carousel) always render the shared placeholder treatment; only `scroll`/`concept` (video) types are `existsSync`-gated to render the real asset once present.** Mirrors the Phase 2/3 precedent for the avatar and company logos (no `public/media/` files exist yet) while still honoring `docs/ASSETS.md`'s explicit, stronger promise specifically for video: "The `<video>` element is already wired, so adding the real file needs no code change." Swapping in real screenshots later is Phase 9 code work; swapping in real concept/scroll videos needs none.
2. **Placeholder carousels are fully interactive (crossfade, dot indicators, pause on hover/focus), not just a single static frame**, cycling through each slide's `alt` text as its label. This lets the carousel *interaction* be verified now, per this phase's own acceptance criterion ("carousels pause on hover and focus"), even though the slide contents are placeholders. Matches the export's own behavior (its placeholder carousel also crossfades).
3. **Found and fixed a real bug during browser testing: the carousel's pause-on-hover/focus never fired.** `ProjectCard`'s "whole card is one link" requirement is implemented via a stretched-link `::after` pseudo-element (the `<a>` wraps only the title text, with `after:absolute after:inset-0` extending its clickable/hoverable area over the whole card) — standard practice for single-link cards. But this means the `<a>`'s stretched area physically sits on top of the media region in hit-testing, so a `ProjectCarousel` component tracking its own `onMouseEnter`/`onMouseLeave` never received those events; confirmed via `document.elementFromPoint` returning the `<a>`, not the carousel's wrapper div, at the media area's center. Fixed by lifting hover/focus state to a new `ProjectCardInteractive` (client) component that wraps the whole card and passes `paused` down as a plain prop — the architecturally correct fix, not a workaround, since it also means the border-color and media-scale hover effects (previously done with a CSS `:has()` trick) now share the same single state source. Verified the fix with real CDP-level mouse hover/leave and keyboard focus, each checked against which carousel slide was actually visible (`opacity:1`), after an initial flawed test (checking the first-matching DOM node's text, which never changes) gave a false negative.
4. **`ProjectMedia.tsx` repurposed from a server component into a plain data-resolving function** (`resolveProjectMedia`), with a new `ProjectMediaView.tsx` doing the actual client-side rendering. Required by the fix in #3: a Server Component can pass pre-rendered JSX or plain serializable data to a Client Component as props, but not functions/closures, and the existsSync check must run server-side while the hover-driven `paused` prop must reach the carousel from a client ancestor — splitting resolution (server) from rendering (client) is the only way to satisfy both.
5. **Project `year` fields are single approximate years** (e.g., Quickbill projects all show "2025"), not real per-project dates — `docs/CONTENT.md`'s company table only gives company-level date ranges, not per-project ones. Each project's year is its company's start year, clearly a placeholder stand-in, not a sourced fact.
6. **`.timeline-highlight` (stubbed in Phase 3) now defined and verified end-to-end**: clicking a company's "N projects →" link on the timeline now visibly flashes that company's card borders accent-red for 1.2s. Confirmed via `document.querySelectorAll('.timeline-highlight')` returning exactly the 4 Quickbill cards when clicking Quickbill's link.
7. **Quickbill Platform's 8 placeholder features and the other 10 projects' 3 placeholder features each** are present in the content layer (`src/content/projects/*.ts`) per `docs/CONTENT.md`'s explicit instruction, but are not yet rendered anywhere — Phase 4 only builds the gallery cards (title/summary/media/skills/company/year). The feature blocks, overview and outcome text will be used starting Phase 5 (project pages and modal).

## 2026-10-11 — Phase 5 Project pages and modal

1. **`ProjectContent` is variant-aware (`"page" | "modal"`), not byte-identical between the two wrappers.** `docs/ARCHITECTURE.md` section 4 says "the modal and the full page render the same `ProjectContent` component. Only the wrapper differs" — but the design export's actual modal markup (`Portfolio.dc.html`, reviewed in Phase 0) shows deliberately *less* content than the full page: features capped at 4 with a "+N more on the project page" note, and no "Outcome and learnings" section at all. Per `CLAUDE.md`'s source-of-truth order, the concrete export wins over ARCHITECTURE's simplified prose on this layout decision. Resolved by keeping one shared component (satisfying the DRY/shared-logic intent) parameterized by `variant`, rather than two disconnected implementations.
2. **Found and fixed a cross-cutting bug while building the first non-home routes: `Nav`'s section links used bare `#id` hrefs**, which only ever worked by accident because every previous phase's testing happened on the home page. Visiting a project page would have made every nav link a dead in-page anchor jump to nothing. Fixed by switching to next-intl's `Link` with `/#id` hrefs, which correctly resolves to `/{locale}#id` from any route, verified by checking the rendered `href` values became `http://localhost:3000/en#experience` etc. (previously bare `#experience`).
3. **Native `<dialog>` + `showModal()` delivers focus-trapping, Esc-to-close, inert background, body-scroll-lock, and focus-restore-on-close entirely for free**, per the HTML living standard — confirmed by testing each one directly (focus landed on the Close button on open; scroll position matched exactly before/after open+close via all four close paths; `document.activeElement` was the originally-clicked card's link immediately after closing). The component only needed to: call `showModal()` on mount, and funnel the dialog's native `close` event (fired by Esc, `.close()`, or a `<form method="dialog">` submit) into `router.back()`. No manual focus-trap, scroll-lock, or focus-restore code was written.
4. **The modal's Close button is a native `<form method="dialog"><button>` rather than a client `onClick` handler** — closing a `<dialog>` via form submission is standard HTML, needs no JS, and funnels through the same `close` event listener as Esc/backdrop/`.close()`, so there's exactly one code path for "the modal closed" regardless of which UI triggered it.
5. **The modal's "Open project page ↗" link uses a plain `<a href="/{locale}/projects/{slug}">`, not next-intl's `Link`**, deliberately forcing a full browser navigation instead of a soft client transition. A soft transition to the same href that's already intercepted would just re-render the same modal; a hard navigation is required to actually land on the real, non-intercepted full page — matching the control's explicit intent ("Open project page").
6. **Prev/next cycling order (both the full page and the modal) walks the single `projects` array** (featured tier first in card order, then other tier, each internally ordered), not separate per-tier cycles — so "Next" from the last featured project goes to the first "other" project, and wrapping from the very last project returns to the very first. Not specified by any doc; a reasonable default given there's only one documented ordering (the gallery's own tier+order sort) to walk.
